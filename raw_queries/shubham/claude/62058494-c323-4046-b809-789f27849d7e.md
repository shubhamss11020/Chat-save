## Deep-dive report — bugs confirmed by actually running the code

I set up dummy env vars, installed the real dependency versions, and ran each module/function against real inputs rather than just reading source. Here's what broke, with the test that proved it.

---

### 1. Redaction safety-net can be bypassed by span ordering — CRITICAL
**File:** `mcp_server/redaction.py:279-295` (`_replace_in_structure`)

The LLM returns a list of exact text spans to strip, then the code does sequential `str.replace()` calls in whatever order the model returned them. I fed it a realistic case:

```
Input: "Jamie Hansen was terminated for cause on 2026-06-01 after repeated policy violations."
Model flags (in this order): ["Jamie", "Jamie Hansen was terminated for cause on 2026-06-01 after repeated policy violations."]

Actual output: "[restricted] Hansen was terminated for cause on 2026-06-01 after repeated policy violations."
```

Because the short span "Jamie" is replaced first, the longer span no longer exists as a literal substring by the time its own replacement runs, so `.replace()` silently matches nothing — **the entire disciplinary-action sentence ships to the caller unredacted**, except the first name. This is exactly the redaction mechanism the codebase's own comments call "the last line of defense" for tier1/HR content, and it fails whenever the model emits an overlapping shorter span before a longer one containing it — which it has no reason not to do, since nothing in the prompt or code sorts spans by length or de-overlaps them before applying.

**Fix direction:** sort `spans` by length descending (longest-first) before building `replacements`, so a shorter span never gets applied before a longer span that contains it.

---

### 2. One malformed citation reference crashes ALL citation resolution
**File:** `wiki_ingestion/citation_resolver.py:64-70` (`_candidates`), called from `resolve_pass`

`resolve_pass` loops over every `unresolved` citation row and calls `_candidates`, which does `date(int(year), int(month), int(day))` with no range validation. I simulated a batch with one bad row followed by a resolvable one:

```
Row 1: source_ref_raw = "raj_gmail-2026-13-05-pricing-review"   (month=13)
Row 2: source_ref_raw = "raj_gmail-2026-05-02-client-meeting-notes"  (valid, would resolve)

Result: resolve_pass CRASHED with ValueError: month must be in 1..12, not 13
```

Row 2 is never reached. Since there's no per-row `try/except` inside the loop, **a single malformed reference (regex doesn't validate month/day range, just digit count) blocks every other pending citation from resolving** on every run until someone manually fixes or deletes the bad row.

---

### 3. Multi-line contradiction/unverified flags are silently truncated to their first line
**File:** `parsers/wikilinks.py:27-38` (`extract_flags`)

Real markdown blockquotes span multiple `>`-prefixed lines. I fed it one:

```
> ⚠️ CONTRADICTION: The invoice says Net-30
> but the contract says Net-60.
> This needs review.

Result: [{'flag_type': 'contradiction', 'text': 'The invoice says Net-30'}]
```

The regex (`^\s*>\s*⚠️\s*CONTRADICTION:\s*(.+)$`, `re.MULTILINE`) only captures up to the first newline. The rest of the contradiction — the actual substance of what's wrong — is dropped with no error, no warning, nothing in logs. Anyone writing (or an LLM agent generating) a multi-line contradiction/unverified block loses everything past line 1.
