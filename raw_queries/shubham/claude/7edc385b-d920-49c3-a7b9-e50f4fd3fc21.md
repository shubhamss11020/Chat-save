## Claude (2026-09-21T10:46:06.252Z)

This codebase is **Cruz (`eoxs-wiki-db`)**, EOXS's internal "second brain". It collects company data (emails, calls, client updates), turns it into a searchable wiki, and lets people query it through chat. I read `ARCHITECTURE.md`, `CLAUDE.md` and the file listing. I haven't read the Python source itself, so the module-level details below come from those docs and the filenames.

## The pipeline

1. **Ingestion** (`ingestion/`). Fetchers pull data from:
   - Gmail (3 inboxes) and Zoho support mail
   - Fireflies and Fathom call recordings
   - Odoo and the implementation boards of steel-industry clients
   - curated internal docs ("assets"), imported by hand

   Sources are checked in real time where possible, plus a 2-hour "sweep" as a safety net.
2. **Filtering and sensitivity labeling** (`spam_filter.py`, `tier_classifier.py`, `inline_tier_classifier.py`). A first AI pass drops noise such as marketing and spam. A second pass labels each item by sensitivity: general, HR/payroll, company-confidential, or Raj-personal. When unsure, it picks the more restrictive label.
3. **Storage.** Everything goes into one Postgres database (`schema/`, `loaders/`), tagged by client and access tier.
4. **Wiki synthesis** (`wiki_ingestion/`). Every 6 hours, an AI process (Claude run as a subprocess) writes cross-linked wiki pages with citations. A second AI checks the citations against the source material. A human still approves a page before it goes live.
5. **Serving** (`mcp_server/`). MCP connectors expose read-only search and get tools over the wiki and raw data. Chat clients, including the frontend, use these.

## Access control

There are several connection identities:

| Identity | Sees | Stripped |
|---|---|---|
| `full` (Raj) | everything | nothing |
| `hr` | confidential and general | dollar amounts except payroll |
| `general` | confidential and general | all dollar amounts and employee-monitoring data |
| `intern` | general only | all dollar amounts |
| `staging_qa` | a sandbox that routes to a separate staging database | n/a |

Access is enforced twice: at the database level, and by an AI check on each response.

## Other pieces

- **`deploy/`**: systemd services and timers, nginx configs, fail2ban and a health check (the `healthcheck.sh` you have open). It also holds the "skill" files that tell Claude how to use each identity's connector.
- **`docs/`**: deep-dive docs. Start with `docs/migration-status.md`.
- **Linear reporting** (`linear_report.py`, `watchtower_*.py`): a one-way status log of what the automation is doing.
- **Infrastructure**: the system moved from Hetzner to DigitalOcean on 2026-08-20, and both servers are currently running in parallel. Tickets and invoices were removed from Cruz and now live only in Odoo. The employee directory was also removed on 2026-09-16.
- **Known gaps** listed in the docs: no database backups yet, and no domain name yet.
