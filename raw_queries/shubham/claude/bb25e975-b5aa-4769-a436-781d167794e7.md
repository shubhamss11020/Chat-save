## Overview: eoxs-wiki-db ("Cruz")

**What it is:** EOXS's internal "second brain" — it continuously ingests company data from Gmail, Zoho support, call recordings (Fireflies/Fathom), and client boards, classifies it by sensitivity tier, stores it in Postgres, and runs an AI pipeline (via `claude -p` subprocesses) that synthesizes the raw data into a cross-linked, cited internal wiki. People then query that wiki through MCP connectors on claude.ai, with access scoped by identity (full/hr/general/intern/staging_qa/ayan).

### Tech stack
Python + FastAPI/uvicorn, PostgreSQL (`psycopg2`), Anthropic SDK for classification/redaction/synthesis, MCP protocol (`mcp==1.29.0`), Gmail/Zoho OAuth libs, document parsers (pypdf, openpyxl, python-docx, bs4). No Docker, no CI/CD workflows.

### Architecture (3 pipelines + a query layer)
- **[ingestion/](ingestion/)** — pulls raw data from each source, classifies sensitivity, runs as a webhook server + periodic sweep job.
- **[wiki_ingestion/](wiki_ingestion/)** — the AI synthesis pipeline: detects new/changed content, drafts wiki pages via Claude, resolves citations, and promotes drafts to publish (human-gated).
- **[mcp_server/](mcp_server/)** — the query-time layer clients actually talk to: stdio and HTTP/SSE MCP servers, per-identity DB routing, query-time redaction.
- **[loaders/](loaders/)** + **[parsers/](parsers/)** — DB loaders and content extraction utilities shared by the above.
- **[schema/](schema/)** — 38 sequential numbered SQL migrations, applied via `run_migrations.py`.

### Deployment
Mid-migration between two targets:
- **Hetzner VPS** (systemd, in [deploy/](deploy/)) — the original/current system of record. Includes the `eoxs-healthcheck.service`/`.timer` you have open — a journalctl-based health check with an optional dead-man's-switch ping — plus services for ingestion, MCP, wiki pipeline, sweep, and pgweb (DB browser), fronted by nginx.
- **DigitalOcean App Platform** (`.do/app.yaml`) — target for the stateless pieces only (MCP, ingestion web service, sweep job); the wiki pipeline stays on a droplet since it spawns Claude subprocesses.

Per `CLAUDE.md`, both environments currently run in parallel, there's no domain yet (raw IPs), and no backups/uptime monitoring exist yet.

### Data model
Two Postgres databases (`eoxs_wiki` live, `eoxs_wiki_staging`) plus a `wiki_staging` schema inside the live DB for draft review. Migration progression: extensions → clients/emails → wiki tables → ingestion state → tickets/invoices/calls → wiki-ingestion tables → access-tier columns → redaction log → employees (first write-capable table) → OAuth accounts → assets → repo_docs → citation indexes.

### Testing
Minimal — only one smoke test file (`parsers/_smoke_test.py`), no pytest setup.

Here's the full picture, based on deep inspection of the actual code (not just structure).

## What "monitoring" exists today — and its gaps

- **Logging**: plain `logging` module → stdout → journald only. No file logs, no aggregation, no structured/JSON logs, no correlation IDs.
- **Health checks**: `deploy/healthcheck.sh` runs hourly, checks `systemctl is-active`/`is-failed` for 6 services + greps `journalctl` for an error pattern in the sweep logs. It's a **pull-based script**, not a dashboard — output goes nowhere except a Healthchecks.io dead-man's-switch ping (silence-on-failure alerting, no detail).
- **Errors are mostly swallowed**: per-source ingestion errors become `{"error": str(e)}` dicts, logged, and the process moves on — never raised, never persisted to a dedicated errors table.
- **No metrics/telemetry library** anywhere (no Prometheus, statsd, OpenTelemetry).
- **No existing dashboard/UI** of any kind — confirmed via repo-wide grep.
- **Claude usage/cost is essentially untracked**: of 11 Claude API call sites, only one (`wiki_ingestion/merge_live_duplicates.py`) computes and logs `cost_usd` from `usage.input_tokens`/`output_tokens`. Everything else (classifiers, redaction, citation resolver, attachment extraction) discards the usage response. The biggest cost driver — `headless_agent.py`, which shells out to `claude -p` as a subprocess for all wiki synthesis — **cannot** capture token usage at all as currently written, because subprocess stdout doesn't carry API usage metadata the way the SDK does.
- **Some state does exist in Postgres** you could build on: `sync_cursors` (per-source last-synced time), `ingest_log` (one row per sweep/webhook trigger), `mcp_redaction_log` (when redaction caught something a classifier missed), `schema_migrations`. But there's **no generic `job_runs`/`pipeline_status` table** — wiki pipeline phase status only goes to Linear (external, not queryable from Postgres).

## Feature inventory (everything that could independently break)

**Ingestion layer** (`ingestion/`)
- 5 fetchers: Gmail, Zoho, Fireflies, Fathom, Odoo — each per-account/per-client, errors caught individually
- Sweep job (2h timer) — orchestrates all fetchers, reports to Linear + `ingest_log`

## Is a real-time dashboard feasible? Yes — but it needs new infrastructure, not just a UI

The gap isn't "no dashboard exists," it's that **there's nothing structured to dashboard yet**. To get what you're describing (live status per feature, per-model Claude usage, upload/CLI/API failures surfaced immediately), you'd realistically need three layers:

1. **A structured event/metrics store** — a new Postgres table (or set of tables) like `job_runs` (feature name, start/end, status, error detail) and `llm_usage` (call site, model, tokens, cost, timestamp), written to from every fetcher, pipeline phase, classifier call, and MCP request. This is the actual gap — today only Linear and journald get this info, and inconsistently.
2. **Instrumentation at each call site** — wrapping each of the ~15+ independently-failing features (5 fetchers, sweep, webhook routes, 6 pipeline phases, MCP servers, each Claude call site) to emit a status/usage event instead of silently swallowing or only logging to journald. The `claude -p` subprocess path is a special problem — it can't report token usage without either switching it to SDK-based calls or parsing whatever `claude -p` prints.
3. **A dashboard frontend** reading that store — could be as simple as a small FastAPI/Streamlit page querying Postgres directly (cheap, fits the existing stack), or push events to something like Prometheus + Grafana (more standard "real-time monitoring" look, more infra to run on top of a repo that already admits "no backups, no uptime monitoring exist yet").

Given the existing stack (Postgres + FastAPI, no Docker/CI, systemd-based deploy, explicitly early-stage infra), the lowest-friction path would be: new Postgres tables for job runs + LLM usage → lightweight instrumentation added at each existing try/except and Claude call site → a small FastAPI + simple frontend (or an artifact-style page) polling/streaming from Postgres. A Prometheus/Grafana stack is more "textbook real-time monitoring" but is a bigger operational lift for infra that currently has no monitoring stack at all.

## Expanded panel design

**1. Service Uptime** (as before)
Webhook server, MCP servers per identity, internal wiki MCP, pgweb, nginx, Postgres.

**2. Job/Pipeline Runs** (as before)
Sweep (2h), wiki pipeline phases (6h), manual CLI runs, healthcheck itself.

**3. Claude Usage & Cost** (as before)
Per call-site volume/tokens/cost/model/error rate across all 11 sites.

**4. Data Freshness / Staleness** — *new, distinct from "did the job run"*
A job can run and report "success" while a specific source silently produces zero new rows (auth token expired, webhook subscription lapsed, API rate-limited but not erroring). `sync_cursors.last_synced_at` per source already exists but nothing watches it. This panel answers "is data actually flowing," not "did the process exit 0" — those are different failure modes and this repo has already swallowed several errors into `{"error": ...}` dicts that a "job succeeded" view would hide. Alert threshold: source X hasn't advanced past N hours when its expected cadence is 2h.

**5. Classification Quality / Redaction Drift** — *new*
`mcp_redaction_log` records every time the query-time redaction safety net caught something the upstream tier classifier missed. A rising rate here means the Claude-powered classifiers (tier_classifier, inline_tier_classifier) are degrading — a real security-relevant signal, not just an operational one, since this whole system's purpose is tiered access to sensitive data. This deserves its own panel rather than being buried under Claude Usage, because the metric that matters is a *rate/trend*, not volume or cost.

**6. Auth/Token Health** — *new*
Gmail (x2), Zoho, Fireflies, Fathom, Odoo all depend on OAuth tokens or API keys that expire or get revoked. A dying token doesn't crash the sweep — it produces a per-source `{"error": ...}` that gets logged and skipped, same failure shape as #4 but a different root cause requiring different action (someone needs to re-auth via `oauth_gmail.py`/`oauth_zoho.py`, not "restart the service"). Worth separating from generic job errors so the dashboard can point at "go run the OAuth flow" rather than "go read logs."

**7. Wiki Pipeline Backlog / Throughput** — *new*
Not just "did each phase run" but: how many candidate pages are queued at detect, how many drafted-but-not-reviewed, how many reviewed-but-not-promoted. A phase can succeed every cycle while a growing backlog quietly indicates review/promote isn't keeping pace with draft volume (or vice versa — human reviewers falling behind an automated drafting step). This is a queue-depth metric, structurally different from pass/fail status.

**8. Security/Access Events** — *new*
Employee/asset write tool usage (the only write paths from the query layer, restricted to full/hr) is a small, sensitive surface — worth a dedicated panel just logging every write with who/what/when, separate from general MCP query volume, since a spike or an unexpected identity using it is the kind of thing you want visible immediately rather than mixed into general traffic.

**9. Infra/Resource Headroom** — *new*
`CLAUDE.md` already flags this repo has no backups and no uptime monitoring, running on a VPS mid-migration to DO. Disk space (Postgres growth, journald growth since there's no log rotation mentioned), and the DO vs Hetzner dual-running state itself (is traffic hitting the box you think it's hitting) are the kind of infra facts that cause outages this system currently has zero visibility into.

## Why these nine, not more

I'd stop there — further slicing (e.g., separate panels per individual fetcher) is better handled as drill-downs within panel 2/4 rather than top-level panels, or the dashboard becomes noise instead of signal. Panels 4–9 exist because each one catches a failure mode that panels 1–3 structurally cannot: silent data staleness, quality drift, auth expiry, backlog buildup, security-relevant writes, and infra exhaustion are not "is it up" or "did it exit 0" questions.

## Making it notify in real time, not just display

For "notifies each issue efficiently" specifically, the panels above split into two alerting shapes:

- **Threshold/absence alerts** (push-worthy immediately): service down, job didn't run within expected window, source stale beyond cadence×N, auth error detected — these map well to the existing dead-man's-switch pattern (`HEALTHCHECK_PING_URL`), just needs per-feature pings instead of one whole-system ping, or a proper alert channel (Slack/email) keyed per panel.
- **Trend/rate alerts** (should not page immediately, but should surface visibly): redaction drift rate, cost run-rate, backlog growth — these want a dashboard graph plus a "rate exceeded X over Y time" soft alert, not instant notification, or you'll get alert fatigue on things that are naturally noisy.

That distinction — hard failures get pushed, trends get watched — is probably the single most important design decision for "robust and efficient," since the current healthcheck script already shows the failure mode of the opposite approach: one coarse success/fail signal per service, which is why you don't currently know about classification drift, staleness, or auth expiry until someone notices data missing.

## Claude (2026-09-11T11:25:47.654Z)

Here's the requirements breakdown, split into what the dashboard needs to *consume*, what it needs to *be*, and what has to change in the existing codebase to feed it.

## 1. Data collection requirements (instrumentation)

The dashboard can only be as real-time and fault-tolerant as its inputs. Right now nothing emits structured events — everything ends up in journald or Linear. Requirements:

- **A write path that survives the thing being monitored crashing.** If a fetcher writes its status only at the end of a run, a crash mid-run reports nothing — you need a "started" event written before work begins and a "finished/failed" event after, so a missing "finished" row is itself the failure signal (heartbeat pattern), not silence.
- **Every independently-failing unit instrumented separately**, not just the parent job — e.g., each of the 5 sweep sources needs its own start/end/error event, not one row for "sweep ran." Same for each wiki pipeline phase, each Claude call-site (currently only 1 of 11 captures usage).
- **Idempotent, at-least-once writes.** Since sources like `ingestion/server.py`'s per-source try/except already isolate failures, the event write itself must not be able to take down the fetcher — wrap it in its own try/except with a local fallback (e.g., write to a local file/queue if Postgres is unreachable) so a monitoring outage doesn't become a data-ingestion outage.
- **A consistent event schema** across all sources (job name, phase, status, started_at, finished_at, error detail, source system) so the dashboard doesn't need bespoke parsing per feature.

## 2. Storage requirements

- **A store independent of the systems it's monitoring wherever possible.** If monitoring data lives only in the primary Postgres DB and that DB goes down, you lose observability exactly when you need it most. At minimum this needs to be weighed: same DB (simpler, but a single point of failure for both data and monitoring) vs. a separate lightweight store (more resilient, more infra).
- **Retention/rollup policy.** Raw per-call Claude usage events and per-item ingestion events will grow fast (11 call sites × high classifier volume) — needs aggregation (hourly/daily rollups) so the dashboard stays fast and storage doesn't grow unbounded, especially since this repo currently has no backup strategy at all.
- **Write throughput headroom.** Classifiers alone (tier, spam, call-relevance) can fire per-email/per-call — the event-writing path must not become a bottleneck on the ingestion path itself.

## 3. Delivery/transport requirements (for "real-time")

- **Decide push vs. poll up front**, since it determines the rest of the stack:
  - *Poll-based* (dashboard queries Postgres every N seconds) — simplest, fits the existing stack (FastAPI + Postgres, no new infra), "real-time" in practice means near-real-time (few-second latency), good enough for operational monitoring.
  - *Push-based* (websocket/SSE from a central collector) — true real-time, but requires a long-running collector process, more moving parts, more to keep fault-tolerant itself.
  - Given this repo's current state (no Docker, no message queue, systemd-only deploy), polling against Postgres is the lower-risk fit; a push layer can be added later without changing the instrumentation.
- **Backpressure/failure isolation between collection and display** — a slow or crashed dashboard frontend must never block or slow down the ingestion/pipeline processes writing events. This argues for a queue or simple insert-and-forget write, never a synchronous call from a fetcher to the dashboard itself.

## 4. Alerting requirements

- **Separate channel from the dashboard UI itself.** A dashboard nobody is looking at when something breaks isn't real-time in the way that matters — needs push notifications (Slack/email/PagerDuty-style) for the hard-failure panels (service down, job absent, auth expired), building on the existing `HEALTHCHECK_PING_URL` dead-man's-switch pattern but per-feature instead of whole-system.
- **Deduplication/rate-limiting on alerts.** A source failing on every 2h sweep for a day shouldn't generate 12 identical pages — needs an "already alerting for X" suppression window.
- **Clear hard-alert vs. soft-trend distinction** (established last turn) — threshold/absence alerts push immediately; rate/trend panels (redaction drift, cost run-rate, backlog growth) surface on the dashboard but don't page, to avoid alert fatigue.

## 5. Fault tolerance requirements — for the monitoring system itself

This is the part easy to skip: the dashboard must not become a second single point of failure.

- **Monitoring must degrade independently of the thing it watches.** If Postgres goes down, both the app and a same-DB dashboard go dark simultaneously — the dead-man's-switch (external, third-party-hosted ping) is the one thing in the current setup that already survives this correctly, and that pattern (external, independent-of-your-infra) should extend to at least the top-level "is anything alive" signal.
- **The dashboard's own uptime needs to be monitored** (who watches the watcher) — at minimum an external ping on the dashboard/collector process itself.
- **Graceful handling of partial data.** If one feature's instrumentation breaks or lags, the dashboard should show "unknown/stale" for that panel, not silently drop it or crash the whole page.
- **No new single point of failure introduced by the monitoring stack itself** — e.g., if you add a message queue or separate collector process, that process needs its own restart/health story (systemd unit + timer, consistent with how everything else in this repo is already run).

## 6. Access/security requirements

Given this repo's whole purpose is tiered access control:

**Summary of the core tension to resolve before design:** true fault-tolerant real-time monitoring (separate store, push transport, independent infra, external alerting) is more infrastructure than this codebase currently runs anywhere else, while a pragmatic version (new Postgres tables, instrumented call sites, polling dashboard, existing dead-man's-switch extended per-feature) fits the current stack with much less new surface area to maintain — and itself avoids becoming the next unmonitored single point of failure. ## What Linear already does in this repo (and does well)

Per `docs/linear-integration.md`, `linear_report.py` already:
- Creates a parent Linear issue per sweep run, with a child sub-issue per source, updated with row counts and item names when each source finishes
- Creates a parent issue per wiki-pipeline phase run, with a child issue per `claude -p` sub-agent invocation
- Maintains one **persistent, continuously-updated** issue (`wiki_ingest_board_state` → `pending_drafts` board) that acts as a live-ish status board inside Linear rather than spawning a new issue every time
- Sets Todo/Done state based on whether errors occurred, so a scan of the Linear board already tells you "did this run finish clean"
- Degrades safely — a Linear outage never fails the pipeline itself (wrapped in `_safe()`)

So for panels like **job/pipeline run history** and **per-source/per-phase outcome**, Linear is already doing real work here, and extending it (e.g., a similar persistent board per ingestion source, or per Claude call-site) is cheap since the pattern and GraphQL client already exist.

## Where Linear structurally can't do the job

- **No real-time push/alerting.** Linear has no concept of paging someone, Slack-routing, on-call escalation, or "notify within seconds." Someone has to be looking at the board, or you'd need to bolt on Linear's own notification rules (email/Slack on issue creation) — which gets you *a* notification, but not dedup, escalation, or severity-aware routing the way Better Stack's incident management does.
- **No heartbeat/absence detection.** Linear only knows about events you explicitly report. If a whole service crashes and stops calling `linear_report.py` entirely, no issue gets created — Linear has no way to notice *silence*, which is exactly the failure mode the dead-man's-switch pattern (Healthchecks.io/Better Stack heartbeats) is designed for. This is a hard gap, not a configuration one.
- **No metrics/time-series/charts.** Claude usage/cost trends, redaction drift rate, backlog depth over time — these want graphs, not issues. Linear has no charting or numeric-trend surface; every one of those would have to be jammed into issue titles/descriptions as text, which is unreadable at any volume.
- **No uptime checking.** Linear doesn't ping URLs. It has zero visibility into whether the MCP HTTP server or webhook server is actually reachable right now — that requires an external prober, which is a different category of tool entirely.
- **Issue-per-event doesn't scale to high-frequency panels.** Classifiers fire per-email/per-call; creating a Linear issue per Claude call site invocation (as currently done per sub-agent call in wiki ingestion) is fine at wiki-pipeline volume but would flood the board at classifier volume — that's exactly why `pending_drafts` uses the "update one persistent issue" pattern instead of spawning new ones, and any extension would need the same discipline.

## Recommendation

Use Linear as the **incident/history surface**, not the monitoring engine: keep (and extend) the existing pattern for panels that are naturally "one row per run" (sweep results, pipeline phase results, per-source outcomes) — that's free, already built, and fits how the team already looks at things. ## Claude (2026-09-11T13:27:35.999Z)

Good question to nail down — here's the honest limitation list, even assuming you write as much code as you want to push data into Linear.

## What code-level Linear pushing genuinely can't fix

**1. Absence/crash detection — the single biggest one**
If code has to run to report "this failed," then when the *whole process crashes* before that reporting code executes, nothing gets pushed at all. Linear then shows... nothing — no issue, no signal, just silence. You can't tell the difference between "everything's fine" and "the reporter itself never ran." This is why external watchers (Healthchecks.io/UptimeRobot) exist — they detect the *absence* of an expected signal from outside, which code running *inside* the thing that might crash can never do for itself.

**2. No real-time paging or escalation**
Linear can email or Slack-notify when an issue is created (via its own notification settings), but that's it — no phone calls, no on-call rotation, no "escalate if unacknowledged in 10 minutes." If you want that, you'd have to build the entire escalation system yourself on top of Linear's API — a much bigger undertaking than the reporting code itself.

**3. Rate limits and issue-flood risk**
Linear's GraphQL API is rate-limited. If code pushed an issue for every low-level event (each classifier call, each email processed), you'd hit those limits fast, and the board would become unreadable — hundreds of near-duplicate issues. This is exactly why the existing `linear_report.py` batches into one parent issue per run with child issues, rather than one issue per tiny event — and why a sweep that fails every 2 hours for a week would create dozens of duplicate issues unless you also build de-dup logic (check for an existing open issue before creating a new one) — extra code on top of the reporting code.

**4. No charts, no trends, no numeric dashboards**
Linear issues are discrete text records. There's no way to get a real uptime percentage graph, a Claude cost-over-time line chart, or a live number — Linear simply has no charting engine. Anything you want visualized as a trend has to be built and displayed somewhere else entirely.

Nobody's staring at Linear waiting for something to change — someone has to actively open it. Without pairing it with real notification/alerting (which itself has limits, per #2), "it's in Linear" doesn't mean "someone saw it in real time."

**6. A Linear outage blinds you exactly when it matters**
If Linear itself is down when a failure happens, the report has nowhere to go — unless you build a fallback (write locally, retry later), which is more code to maintain.

## So, direct answer

Writing more code absolutely gets you **richer detail** — proven already by the existing wiki-ingestion pattern in the screenshot you showed earlier. But it cannot solve **absence detection**, cannot give you **paging/escalation**, cannot give you **charts/trends**, and risks **flooding the board** without deliberate de-dup work. That's precisely why the plan pairs the two: code-level Linear reporting for rich detail on things that already run and get caught, plus an external watcher (Healthchecks.io/UptimeRobot) specifically for "did this even run at all" — one tool alone, no matter how much code you write for it, can't cover both roles.

## The mechanism, precisely

**It's a direct, synchronous HTTP call to Linear's GraphQL API — not a queue, not a batch job, not deferred.** Every `_create_issue()` / `_update_issue()` call in `linear_report.py` is a plain `httpx.post()` to `https://api.linear.app/graphql`, and it happens **the instant** that point in the code is reached — no delay, no polling, no retry queue.

## Where it's actually wired in (`ingestion/server.py:119-177`, `run_full_sweep()`)

```
parent_issue_id = start_sweep_parent()          # ← Linear issue created NOW, before any source runs
for name, fn in [gmail, zoho, fireflies, fathom]:
    task_issue_id = start_source_task(parent_issue_id, name)   # ← child issue created NOW
    summary[name] = fn()                          # ← the actual fetch happens here
    finish_source_task(task_issue_id, name, summary[name])     # ← that same child issue UPDATED NOW with the real result
finish_sweep_parent(parent_issue_id, summary, run_at)           # ← parent issue UPDATED NOW with the final total
```

So the sequence is genuinely live: a Linear issue for the whole sweep appears **before** Gmail's fetch even starts (so a stuck sweep is visible mid-run, not just after), then each source's own issue gets created right before that source runs and updated with its real result the moment it finishes.

## Where "background" actually applies — and it's a different layer

`run_full_sweep()` (and therefore all of the above) is invoked from `_run_bg()` (`ingestion/server.py:180-199`):

```
counts = await loop.run_in_executor(None, lambda: fn(*args, **kwargs))
```

This offloads the whole sweep (including all the Linear calls inside it) onto a background thread pool, **so it doesn't block the FastAPI server's main event loop** — meaning the webhook server can keep answering other requests (like `/health`) while a sweep is running. That's the only sense in which this is "background": it's not on the server's main async thread. The Linear API calls themselves, once that background thread is running, are still fully synchronous and immediate — each `httpx.post()` blocks for up to its 15-second timeout waiting for Linear's response before the code moves to the next line.

## Fault tolerance built in

Every one of these calls is wrapped in its own try/except that only logs a warning and returns `None`/silently continues (`except Exception as e: logger.warning(...)`) — so if Linear is slow or down, the sweep itself is completely unaffected; you just don't get that particular issue/update, and the actual ingestion work proceeds regardless. This is the exact `_safe()`-style pattern referenced in the docs.

## Answering your original question directly

**Not "background" in the sense of a job queue or async task runner** — it's a live, synchronous API call made at the exact moment each phase starts/finishes, from inside a background *thread* (not a background *queue*) so it doesn't block the web server. If you build the MCP tool-call reporting discussed last message, the natural approach is the same: a direct synchronous `httpx.post()` call to Linear right inside `call_tool()`'s except block, wrapped in the same try/except-and-continue safety pattern — no queue infrastructure needed, matching exactly what's already proven here.
