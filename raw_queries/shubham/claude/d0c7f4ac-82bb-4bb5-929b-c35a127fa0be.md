## The real value of a monitor
"Non-ingested data" means an email exists in the mailbox but not in `email_threads`. The monitor finds those by listing the mailbox through the API and comparing it with the DB. A backend can do that job on a schedule without Airflow.

## Suggested architecture

```
Gmail / Zoho API ─┐
Postgres (read-only user) ─┼─► Backend (Node + TS) ──► App DB (users, invites, runs, health)
Drive API ─┘                │  scheduler + workers        │
                            └──► REST + SSE ──► this React dashboard
                                 └──► optional Google Sheets export
```

- **Scheduler and workers:** a cron-style job (pg-boss or BullMQ) runs every few minutes. It reconciles the mailbox against the DB, evaluates the health checks, and writes `pipeline_runs` and `run_events`. Those tables replace the Airflow logs.
- **Live log view:** the existing log console reads from those tables, and SSE (server-sent events) streams new rows to the browser.
- **Real authentication:** login plus server-side client scoping. This also fixes the biggest limitation in the README.
- **Sheets:** an optional nightly export for people who like the spreadsheet. It stops being the data source.

## Trade-offs you should know
1. **It needs a real always-on server.** Vercel functions can't run schedulers or stream logs. A small DigitalOcean droplet (you already have one), Railway or Fly.io works. The React frontend can stay on Vercel.
2. **Independence is the point of a monitor.** If the same code both ingests and checks itself, it can miss its own failures. Keep the monitor read-only and separate from the ingestion daemon.
3. **Daemon logs over SSH are fragile.** It's better if `eoxs-sweep` sends a heartbeat or writes its status to a table. The monitor then alerts when the heartbeat is older than a threshold. Reading `journalctl` remotely is the fallback.
4. **Replacing Airflow's ingestion is a separate, bigger project.** Only do it if you actually want to retire the DAGs.
5. **Access needs approval.** You need a read-only Postgres user and the mailbox API credentials. Both are security decisions for whoever owns them.

## Build it in phases
1. **Phase 1, database first.** Backend with read-only DB queries for the meeting columns and the three health checks. The dashboard reads from the backend instead of Sheets. This is the fastest win and needs no mailbox access.
2. **Phase 2, mailbox reconciliation.** Gmail and Zoho listing, "Non-ingested" detection, and the run log tables with live streaming.
3. **Phase 3, auth and hardening.** Real login, server-side client scoping, and alerts by email or Slack when a check fails.
4. **Phase 4, optional extras.** Sheets export and daemon heartbeat.

## Questions before I start
1. Do you have, or can you get, read-only access to the Postgres database and the Gmail and Zoho credentials?
2. Does Airflow do any of the ingestion, or does the `eoxs-sweep` daemon do all of it?
3. Where would you host the backend: the DigitalOcean server, Railway or Fly, or something else?

If you confirm that, I'd start with Phase 1. It stays compatible with the dashboard you have today.

## Which cache pattern

The usual write patterns don't fit the sheet data well, because your app never writes to the sheet: Airflow does, and the sheet is the source of truth. From your app's point of view that is **write-around**, so the right design is:

**Cache-aside, plus refresh-ahead, plus event-driven invalidation.**

| Pattern | Use here? |
|---|---|
| **Cache-aside** | Yes. Requests read Redis; on a miss, one worker fetches Google and fills Redis. |
| **Refresh-ahead** | Yes. A background task keeps the live tab fresh, so users never wait on Google. |
| **Event-driven invalidation** | Yes. The writer (Airflow, later your own ingestion) pings `POST /api/webhook/sheet-updated` after writing, and the cache refreshes immediately. A TTL stays as the safety net. |
| **Write-through** | Later, when your backend owns ingestion. It writes Postgres, then updates Redis in the same step. |
| **Write-back** | No. Redis can lose data, and it's wrong for passwords, invites and sessions. |

For data you do write (users, invitations): Postgres stays authoritative and Redis is a derived cache. Delete the cached key on any change, so disabling a member still takes effect instantly. Don't write to all three of Sheets, Redis and Postgres: two writable copies of the same data cause drift. Choose one source of truth and treat the others as derived.

## What goes in Redis

- **Sheet snapshot per tab:** past days almost never change, so give them a long TTL. The live tab gets about 30 seconds plus **stale-while-revalidate**: serve the last good copy while one worker refreshes it.
- **Single-flight lock** (`SET NX`): when the cache is empty, only one request calls Google and the rest wait. This prevents a stampede.
- **Stale-if-error:** if Google is down or rate-limiting, keep serving the last snapshot and show "data as of 10:06".
- **Cache the raw snapshot only, never per-user results.** Apply each member's client filter after reading the cache, so one user's data can't be served to another.
- **Rate-limit counters and cached user lookups** (the user row is currently read on every request).
- **Two levels:** a small in-process cache (5–10 s) in front of Redis, to absorb bursts and survive a Redis outage.

Result: Google calls drop from "users × polls" to about **one every 30 seconds, or none when nothing changed**.

## Rate limiting

Redis atomic counters (token bucket or sliding window), returning `429` with `Retry-After`:

| Where | Limit |
|---|---|
| **Sign-in** | Per email (5 failures, then backoff) **and** per IP (about 20 a minute). Counters move from the database to Redis, which also stops failed logins from causing DB writes. After repeated failures, add a CAPTCHA such as Cloudflare Turnstile. |
| `/api/sheet-data` | Per user, about 60 a minute, so one user can't burn the Google quota |
| `/api/invites` | About 20 an hour per admin and 3 a day per target email, to prevent email-bombing |
| Refresh and webhook | Tight limits |

Per-IP limiting only works if the IP is trustworthy. Behind Vercel and Render the backend must read the client IP from the right proxy hop (a "trusted proxy count" setting), or the limit is trivially bypassed.

If Redis is down: the API fails open, and the login limiter falls back to the existing database lockout.

## Other things that cut latency and add robustness

1. **Send invite emails in the background.** The invite request currently waits on SMTP, which can take up to 20 seconds. Use a background task or a queue (RQ or arq on Redis) with retries.
2. **Slim the list payload.** Rows carry full email bodies (up to 49,000 characters each). The list needs a preview only. Fetch the full body when someone opens an email.
3. **gzip plus ETag (304 when nothing changed).** An unchanged poll then returns almost nothing.
4. **Push instead of poll.** The backend sends an SSE event when the cache refreshes, and browsers refetch only then. This removes the 30-second polling entirely.
5. **Circuit breaker and backoff with jitter** for Google calls.
6. **Observability:** cache hit ratio, Google call counts, 429 counts, request IDs, Sentry, and a health check that tests Redis and Postgres.
